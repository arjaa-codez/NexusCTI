## 2. In-Depth Reconciliation of Database Hash Mismatch

`cyber_attribution_engine/data/chroma_db/chroma.sqlite3`

### 2.1 Forensic Explanation of the Discrepancy
1. **Raw File Hash Discrepancy:**
   - Frozen SHA-256: `f1619bf2182fe2cdeef65be2e6785262b5e2e5e0f83a7bbdfa3f9cb67a0232a5`
   - Active Raw SHA-256: `1ddc579d0d8324cd11970189d5652acca303f5840ab7dd7a6ede53bfa4744e11`
2. **Byte-Level Cause:**
   - SQLite header bytes 24–27 store the 32-bit big-endian `file_change_counter`.
   - Each time ChromaDB's default `PersistentClient` establishes a connection, SQLite updates this counter.
   - The file size remains unchanged ($294{,}912$ bytes in Phase 9, expanding to $487{,}424$ bytes following index allocation).
3. **Canonical Logical Content Invariance:**
   - Computing a cryptographic hash across all table rows (`collections`, `embeddings`, `embedding_metadata`) yields:
     $$\text{Canonical Content Hash} = \texttt{668d0776c609e3253143dd4764652ec4e121e082247458e18699a5e63a2faee7}$$
   - This content hash is **100% identical** across all audit runs. The underlying documents, vector representations, and metadata attributes have experienced zero mutations.
